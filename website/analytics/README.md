# Управление сайтом и аналитика на VPS

Сайт остаётся на GitHub Pages. Node.js 24.12+ и встроенный SQLite работают на VPS,
без npm-зависимостей. Сервис слушает **только 127.0.0.1:8787**. Статистика доступна
в закрытой панели `/admin/` после настройки входа, а также через SSH. Сейчас сбор выключен
в `../site.json`, внешние ресурсы и Turnstile на сайте не загружаются.

## Что считается

| Показатель | Определение |
| --- | --- |
| Уникальные посетители | Различные подписанные идентификаторы браузера за выбранные 1–35 дней. Идентификатор живёт до 30 дней, не продлевается при каждом посещении. |
| Посещения | Первое открытие страницы в каждой фиксированной 30-минутной сессии. Вкладки одного браузера по возможности используют общую сессию. |
| Просмотры | Открытия известных HTML-страниц. Переключение разделов документации не создаёт просмотра. |
| GitHub | Клики по ссылкам проекта, включая кнопку скачивания. |
| Скачать | Подмножество GitHub-кликов по явно помеченной кнопке; это намерение скачать, не подтверждение загрузки файла. |
| Страна | Страна IP подключения из локальной MMDB или доверенного Cloudflare. Не гражданство и не точное местоположение. `ZZ` — неизвестно. |

Уникальные за период считаются как DISTINCT, не суммой уникальных по дням.
Посетитель может попасть в несколько стран, поэтому их уникальные тоже не складываются.
Даты отчёта — UTC. Считаются только согласившиеся посетители с JavaScript, прошедшие
проверку; DNT/GPC, отказ, фильтры браузера и недоступность защиты уменьшают охват.
Очистка хранилища или другой браузер меняют идентификатор. Эти метрики не являются
точным числом людей. Не объединять их с данными использования VPN-приложения.

## Защита и её пределы

- Turnstile проверяется на сервере через Siteverify: успех, hostname и action.
  Клиентский ключ публичный; секрет проверки хранится только на VPS. Одноразовость
  challenge обеспечивает Siteverify, срок challenge — 5 минут.
- Сервер подписывает visitor/session токены HMAC-SHA256. Токен сессии живёт 30 минут,
  связан с IP и User-Agent. Подмена токена, IP или аудитории отклоняется. Страна и IP
  из тела события не принимаются. CORS — дополнительная граница браузера, не авторизация.
- Nginx перезаписывает служебные заголовки. Node принимает их только от loopback
  с отдельным секретом прокси. Не открывать Node напрямую, не доверять всему Internet
  через `set_real_ip_from`, не подключать сторонние прокси без пересмотра границы доверия.
- Лимиты: тело 4 KiB, заголовки 8 KiB, таймауты, 128 соединений Node, 8 параллельных
  проверок Turnstile, 120 запросов/мин на IP, 4 выдачи сессии/10 мин на IP,
  IPv6 объединяется по /64. Память таблицы лимитов ограничена 20 000 записями.
- В сессии максимум 40 просмотров и 10 кликов. UUID события устраняет повторный
  подсчёт. Сначала нужен просмотр. SQLite хранит дневной предел 4 000 сессий и
  20 000 событий; перезапуск процесса его не сбрасывает. При достижении лимита
  статистика прекращается, сайт продолжает работать. Учитывайте общие IP/NAT.
- База ограничена примерно 128 MiB, журнал — настройками SQLite, процесс — systemd.
  При нехватке места сервис отвечает 503. Нужны контроль свободного места и обновления ОС.
- В базе нет полных IP, User-Agent, URL, query, рефереров или содержимого страницы.
  Временные идентификаторы хешируются с секретом. Сессии и дедупликация удаляются
  после истечения, суточные идентификаторы — через 35 дней, агрегаты — через 395 дней.
  Очистка работает каждый час и при запросах; резервные копии должны иметь такой же срок.

**Ни токен, ни CAPTCHA не гарантируют нулевую накрутку.** Распределённые реальные
браузеры могут проходить проверки. Лимиты ограничивают ущерб, но могут уменьшать
полноту статистики. Nginx/Node не остановят насыщение сетевого канала VPS: при работе
по IP нужна защита у хостера. После появления домена предпочтителен Cloudflare Tunnel,
закрывающий прямой HTTP-доступ к аналитике. Это не скрывает IP уже работающего VPN.

## Turnstile: бесплатный вариант

В Cloudflare создать **Managed** widget `Mukhomor website analytics`, hostname
`0nionow1.github.io` (без схемы и пути), без pre-clearance. Домен VPS не нужен:
виджет выполняется на GitHub Pages. Ключ виджета записать в `../site.json` как
`analytics.turnstileSiteKey`, секрет — в приватный environment на VPS.
Не использовать Global API Key. Для автоматизации достаточно ограниченного
Account → Turnstile Edit для нужного аккаунта, временный API-токен после настройки отозвать.
Не помещать секреты в чат, репозиторий, frontend или отчёты проверки.

## Установка сервиса (Linux/systemd)

Сначала проверить занятые порты и существующие сервисы: VPS также может обслуживать VPN.
Не заменять действующую конфигурацию Nginx целиком и не останавливать приложение.

1. Установить поддерживаемую Node.js 24 LTS (не ниже 24.12), Nginx и обновления ОС.
   Для Ubuntu 22.04 нужны `nginx-core` и `libnginx-mod-http-geoip2`: сборка
   `nginx-light` не включает обязательные модули `limit_req` / `limit_conn`.
   На 24.12 встроенный SQLite помечен experimental; код использует проверенный здесь API.
2. Создать отдельного системного пользователя `mukhomor-analytics` без входа.
   Копировать `server.mjs`, `store.mjs`, `http.mjs`, `admin.mjs`, `admin-access.mjs`,
   `telegram.mjs`, `telegram-setup.mjs`, `report.mjs`, `content.mjs`, `content-store.mjs` и каталог `admin/` (включая `manage.js`)
   в `/opt/mukhomor-analytics`. Рядом положить `website/content.json` как `content-seed.json`
   и `website/content-fields.json` как `content-fields.json`. В `admin/assets/`
   скопировать `Tiny5-Regular.ttf`, `Tiny5-LICENSE.txt`, `mushroom-mini.svg`
   из `website/public/assets/` (без остальных материалов сайта),
   владельцем исходников оставить root, дать сервису только чтение.
3. Создать `/etc/mukhomor-analytics` root:root 0700. Скопировать `environment.example`
   в `environment` с правами 0600. Сгенерировать **два разных** 32-байтных секрета
   (`openssl rand -hex 32`) и вставить их в соответствующие поля. Добавить Turnstile secret.
   `proxy.headers` в этой же папке, root:root 0600, должен содержать одну директиву:
   `proxy_set_header X-Analytics-Proxy-Key "ЗНАЧЕНИЕ_ANALYTICS_PROXY_KEY";`.
4. Установить пример unit как `/etc/systemd/system/mukhomor-analytics.service`,
   проверить путь к Node, выполнить `systemctl daemon-reload`, затем запустить сервис.
   Каталоги с кодом должны быть доступны служебному пользователю для чтения и прохода
   (например, root-owned `0755`); каталог приватной конфигурации остаётся `0700`.
   systemd создаёт закрытый каталог состояния; база не находится в webroot.
5. Выбрать **один** вариант внешнего доступа ниже. Проверить конфигурацию `nginx -t`
   перед reload, не открывать 8787/8090 во внешнем firewall.

## Сейчас: HTTPS по IP, без домена

`nginx-ip.example` — шаблон отдельного vhost. Заменить документационный IP
`203.0.113.10` на адрес VPS. Нужен Nginx GeoIP2 module (например, пакет
`libnginx-mod-http-geoip2` в Debian/Ubuntu) и локальная Country MMDB. Скачать
[DB-IP Country Lite](https://db-ip.com/db/download/ip-to-country-lite), распаковать
в `/var/lib/mukhomor-geo/country.mmdb` и обновлять ежемесячно атомарной заменой.
База не публикуется в GitHub. Сервер делает локальный поиск, не отправляя IP геосервису.
Данные DB-IP распространяются с атрибуцией CC BY 4.0; ссылка есть на странице данных
и в JSON-отчёте. Не включать аналитику без рабочей базы, иначе страны будут `ZZ`.

Let’s Encrypt выдаёт сертификаты на IP. Для webroot нужен **Certbot 5.4+**.
Сначала включить только HTTP-секцию для ACME, создать `/var/lib/letsencrypt`, затем:

```sh
sudo certbot certonly --preferred-profile shortlived --webroot \
  --webroot-path /var/lib/letsencrypt --ip-address YOUR_VPS_IP \
  --deploy-hook "nginx -t && systemctl reload nginx"
```

После успешной выдачи включить TLS-секцию с фактическими путями сертификата.
IP-сертификат действует около шести дней: **обязательно** включить автоматическое
продление Certbot и проверить `certbot renew --dry-run`. Порт 80 должен оставаться
доступен для ACME. Если 443 занят VPN, выделить согласованный TLS-порт аналитики и
указать его в endpoint; не освобождать порт остановкой VPN. Сертификат проверяет IP,
порт на его действительность не влияет. HTTP и самоподписанный сертификат для Pages
не подходят. Защитные лимиты сервера включены, защита канала остаётся у хостера.

## Позже: домен и Cloudflare Tunnel

После добавления собственного домена в Cloudflare использовать `stats.<домен>`:
создать именованный Tunnel и DNS-маршрут, установить cloudflared. Шаблон
`cloudflared.yml.example` направляет только этот hostname в loopback Nginx;
всё остальное возвращает 404. Использовать `nginx-tunnel.example` вместо IP-vhost.
Включить IP Geolocation в Cloudflare. Не включать Pseudo IPv4 overwrite или
Transform Rule, удаляющий visitor IP. Включить Always Use HTTPS. Не кэшировать
`/v1/*` и `/admin*`, не отключать передачу Cookie и Set-Cookie для панели.

Проверить `CF-Connecting-IP` и `CF-IPCountry` на доверенном пути, затем закрыть
прямой публичный порт аналитики. Временный Quick Tunnel не использовать как адрес
продакшн-аналитики. Встроенные лимиты не зависят от платных правил Cloudflare.

## Закрытая панель владельца

Адрес — `https://IP:TLS_PORT/admin/` (или `/admin/` на собственном домене аналитики).
Панель обслуживает VPS, она не входит в `website/public/` и сборку GitHub Pages.
Она показывает посетителей, посещения, просмотры, клики, дни и страны за 1–35 дней.
Пустая база отображается как нули. Ссылка на вход не нужна на публичном сайте.

В приватном `/etc/mukhomor-analytics/environment` задать **все пять** значений:
`ADMIN_ORIGIN` — точный HTTPS origin с портом, без пути;
`ADMIN_USERNAME` — логин; `ADMIN_PASSWORD_HASH` — scrypt-хеш;
`TELEGRAM_BOT_TOKEN` — токен BotFather; `TELEGRAM_CHAT_ID` — подтверждённый личный чат.
Без настроек `ADMIN_*` панель отключена. Частичная конфигурация не запускается;
для настроенной админки Telegram обязателен, вход только по паролю не предусмотрен.
Пароль, хеш, токен бота, chat ID, сессии и коды не должны попадать в Git или Pages.

Создать хеш на VPS из скрытого ввода (не передавать пароль аргументом команды):

```sh
sudo sh -c 'umask 077; systemd-ask-password "Admin password:" | node /opt/mukhomor-analytics/admin-access.mjs password > /root/mukhomor-admin.hash'
```

Вставить **содержимое файла с хешем** в `ADMIN_PASSWORD_HASH` приватного environment
через редактор от root, сохранить права 0600, затем перезапустить сервис.
После переноса удалить временный файл `/root/mukhomor-admin.hash`.
Смена логина, хеша, секрета сервера, токена бота или chat ID отзывает предыдущие
сессии и ожидающие коды после перезапуска. Старые сессии без второго этапа не принимаются.

### Одноразовая привязка Telegram

Создать отдельного бота через BotFather. Добавить `TELEGRAM_BOT_TOKEN` в приватный
env; не вставлять его в адресную строку браузера, аргументы команд, логи или чат.
Утилита настройки также понимает прежнее локальное имя `TELEGRAM_BOT_SECRET`
и при завершении переводит его в `TELEGRAM_BOT_TOKEN`.

```sh
node website/analytics/telegram-setup.mjs begin --env /absolute/private/environment
```

Команда делает два коротких запроса к Bot API (`getMe`, `getWebhookInfo`) и выдаёт
одноразовую ссылку на 30 минут. Владелец открывает её в своём Telegram и нажимает
**Start / Запустить**. После его подтверждения выполнить:

```sh
node website/analytics/telegram-setup.mjs complete --env /absolute/private/environment
```

Один запрос `getUpdates` с `timeout: 0` находит точную команду с одноразовым секретом.
Принимается только личный чат живого пользователя с совпадающим ID отправителя.
Обычный `/start`, первый случайный отправитель, группа, старое сообщение и несколько
разных отправителей не подходят. `TELEGRAM_CHAT_ID` сохраняется атомарно рядом с
токеном; исходные настройки сохраняются. Временный файл привязки удаляется.
Содержимое чужих сообщений не печатается, их получение не подтверждается через offset.
Существующий webhook не удаляется: для такого бота нужно выбрать отдельный экземпляр.
Если в очереди больше 100 посторонних обновлений, использовать отдельного бота.

Скопировать **оба значения** в приватный environment сервиса и перезапустить его.
Во время обычной работы сервер вызывает только `sendMessage` после верного пароля.
Постоянного процесса бота, webhook, таймера опроса и Telegram SDK нет.

### Второй этап входа

После верного пароля сервер возвращает 202 и временную HttpOnly cookie запроса,
которая **не даёт доступа к статистике**. В личный чат приходит случайный восьмизначный
код и номер запроса; тот же номер показан на странице входа. Код привязан к конкретному
запросу, IP, User-Agent и текущим настройкам владельца. В SQLite хранится только HMAC
кода с секретом сервера. Код действует не дольше пяти минут; после пяти неверных попыток
нужно заново ввести пароль. Проверка и погашение атомарны, повторное использование
и одновременные запросы не создают две сессии. Перезагрузка страницы сохраняет этап ввода.

Отправка ограничена одним сообщением в минуту, пятью в час и двадцатью за день UTC
для всей панели. Неудачная отправка тоже расходует лимит, автоматических повторов нет.
Новый код для того же браузера отменяет предыдущий после успешной отправки.
Лимиты отправки и попытки проверки сохраняются при перезапуске. Таймаут Telegram —
пять секунд, перенаправления запрещены. При недоступности API, блокировке бота или
неподтверждённом получателе вход остаётся закрытым, запасного входа по паролю нет.

Код вводится только на странице панели. Telegram является отдельным каналом
подтверждения, но код можно выманить фишингом; не выдавать эту схему за passkey
или защиту от компрометации самого Telegram-аккаунта. Не публиковать коды и токен.
При утрате доступа к чату восстановление выполняется владельцем через SSH:
повторная привязка, обновление приватного env и перезапуск, без отключения второго этапа.

Защита входа:

- scrypt N=32768, r=8, p=3; случайная соль для каждого хеша, сравнение постоянного
  времени. Одинаковая ошибка для неверного логина и пароля; хеширование выполняется
  в обоих случаях. Одновременно допускаются не более двух вычислений scrypt.
- Не более 5 проверок на IP (IPv6 /64) за 15 минут, 20 со всех адресов за 15 минут
  и 100 за день UTC. Учитываются и успешные входы. Пределы хранятся в SQLite;
  заблокированные запросы не продлевают окно. Это ограничивает распределённый перебор,
  но атакующий может временно лишить владельца новых входов, исчерпав общий бюджет.
- Случайная 256-битная cookie `__Host-`, Secure, HttpOnly, SameSite=Strict,
  без Domain; в базе только HMAC идентификатора. Нет токенов в localStorage.
  Сессия привязана к IP и User-Agent, максимум час и 15 минут без запросов отчёта.
  Панель не опрашивает сервер автоматически, чтобы не продлевать забытую вкладку.
- Origin, Host, схема и Sec-Fetch-Site проверяются отдельно от сборщика статистики;
  API требует специальный заголовок, выход — CSRF-токен. Нет CORS для панели.
  Вход меняет сессию, выход отзывает её на сервере. Токен посетителя не даёт доступа.
- Нет кэширования, встраивания в iframe и индексации. Статические файлы доступны
  только по явному списку. База, environment и служебные программы не раздаются.

Восстановление через уже защищённый SSH-доступ, если общий лимит исчерпан:

```sh
sudo -u mukhomor-analytics node /opt/mukhomor-analytics/admin-access.mjs reset-limits /var/lib/mukhomor-analytics/analytics.sqlite
sudo -u mukhomor-analytics node /opt/mukhomor-analytics/admin-access.mjs revoke-sessions /var/lib/mukhomor-analytics/analytics.sqlite
```

`revoke-sessions` удаляет также все ожидающие запросы кода. Первую команду выполнять
только вручную после оценки причины блокировки (она сбрасывает и лимиты отправки);
автоматически сбрасывать лимиты нельзя. При активной атаке сначала ограничить
`/admin*` по своему стабильному IP на прокси или пользоваться SSH-отчётом.
После появления домена можно добавить Cloudflare Access с MFA перед `/admin*`,
сохранив текущую проверку входа. Access не должен перекрывать `/v1/*`.
Защита от перебора не заменяет защиту сетевого канала у хостера.

Проверять изменения входа тестами из раздела ниже. На реальном VPS отдельно
проверить HTTPS cookie, доставку кода, оба этапа входа, выход, 401 без полной сессии,
истечение и повтор кода, блокировку повторных попыток,
закрытый порт Node и сохранность действующих VPN-сервисов.

## Подключение сайта и проверка

В `../site.json` задать `analytics.endpoint` как `https://IP` (или с TLS-портом,
позже `https://stats.<домен>`), публичный site key и `enabled: true`. Запустить
`node website/scripts/seo.mjs`, `node website/scripts/check.mjs` из корня проекта.
На GitHub Pages публикуется **только `website/public/`**, никогда эта папка или
приватный environment. Публикация сайта по-прежнему требует одобрения владельца.

До запуска проверить на конечном HTTPS-пути: добровольное согласие → Turnstile →
сессия → просмотр → GitHub/скачивание; повтор UUID; чужой Origin; неверный токен;
прямой порт; доверенную страну; отказ и DNT/GPC. Запросы через Nginx и реальный
Turnstile требуют отдельного smoke-теста: локальные тесты его не заменяют.

## Содержимое сайта

Панель управляет текстами и каталогом релизов. `GET /v1/site` выдаёт только последнюю
опубликованную редакцию; до первой публикации возвращает 503. Установка сервиса не
публикует начальный снимок. Публичное чтение имеет лимиты nginx/Node, ETag и max-age=30,
не требует Turnstile, не выдаёт посетительский токен и не пишет аналитику.

`/admin/api/site` и все записи доступны только после пароля и Telegram-кода.
Записи проверяют Origin, CSRF, ревизию и квоты (60 записей/минуту, 10 импортов/час).
Импорт обращается только к GitHub API фиксированного репозитория, с ограничениями
времени и размера и запретом перенаправлений. Произвольные URL и HTML не принимаются.
Большой JSON допускается только у сохранения после авторизации (256 КиБ); лимит
остальных запросов остаётся 4 КиБ. В nginx у /admin/ разрешено 258 КиБ без предварительной
буферизации тела; проверку конкретного маршрута выполняет Node.

В SQLite хранятся черновик, опубликованный документ, до 10 снимков и до 100 записей
журнала; проверенные источники релизов ограничены 200 записями. Восстановление создаёт
новый черновик. Экспорт доступен владельцу и содержит опубликованный снимок без секретов.
Перед обновлением делайте согласованную резервную копию SQLite и каталога приложения;
не перезаписывайте environment, ключи, Telegram-привязку и существующую базу.
Начальный seed не заменяет правки в существующей базе. При изменении набора текстовых
ключей нужна отдельная миграция сохранённых документов; не удаляйте базу ради обновления.

# Работа с историей обновлений

# Поддерживаемые платформы

Windows, Linux и Android — обязательные платформы Mukhomor. Текущая версия
разрабатываемого приложения — 0.8.2. Общие возможности, импорт и правила
должны работать на всех трёх платформах; системная интеграция реализуется
отдельными адаптерами. При изменениях проверяйте сборки и тесты всех платформ.
Успешную компиляцию не выдавайте за проверку VPN: отдельно фиксируйте проверки
маршрутов, DNS, отключения, отказов и жизненного цикла на реальной ОС.
Не объявляйте непроверенные возможности готовыми и не изменяйте историю
опубликованных выпусков при обновлении версии в исходниках.

Каждое обновление собирайте сразу для Windows, Linux и Android. Небольшая правка
сохраняет номер версии и заменяет предыдущую сборку в том же каталоге. Среднее или
крупное обновление повышает patch-номер на единицу (например, 0.8.0 → 0.8.1).
Синхронизируйте Cargo, Android versionName/versionCode, Go и подпись версии в UI.
Готовые файлы храните только в `release-staging/<версия>/<платформа>/<архитектура>/`;
у Android дополнительно разделяйте `debug/` и `release/`. Исходники и SHA-256
лежат рядом со своей сборкой. Временные каталоги сборщиков находятся в `target/`,
не создавайте копии одной версии с GUID в `release-staging` и не используйте `dist`.
Заменяйте готовую сборку только после успешной проверки нового пакета.

При каждом заметном пользователю изменении приложения агент обязан обновить
`CHANGELOG.md` в разделе `## [Unreleased]` и короткую запись `unreleased` в
`website/changelog.json`. Описывайте результат для пользователя: что добавлено,
изменено или исправлено. Не приписывайте текущие правки уже выпущенной версии.

При подготовке нового выпуска перенесите соответствующие заметки в раздел
`## [X.Y.Z]` файла `CHANGELOG.md`. Сверьте номер с Cargo и тегом `vX.Y.Z`.
После подтверждённой публикации GitHub Release импортируйте версию в панели сайта.
Файлы и `publishedAt` берутся из GitHub API. Новый импорт получает статус «В проверке»;
Stable и рекомендацию меняйте только после проверки владельцем. Для статической копии
экспортируйте опубликованный снимок в `website/content.json` командой
`node website/scripts/content.mjs --snapshot ПУТЬ_К_СНИМКУ`. Из `unreleased`
файла `website/changelog.json` удалите только вошедшие в выпуск пункты. Пустой
`unreleased` задавайте как `null`. Не выдавайте тег, локальную сборку или
черновик GitHub Release за опубликованный выпуск.

Записи на сайте идут от новых к старым. Сохраняйте предыдущие версии. Текст
краткий, на русском, только о доступных возможностях, изменениях и исправлениях.
Публичное название собственного протокола — **Mycelia**. Соблюдайте редакционные
ограничения сайта, проверяемые `website/scripts/check.mjs`; не копируйте
технический журнал целиком в пользовательскую страницу.

После изменения заметок выполните:

```sh
node website/scripts/content.mjs
node website/scripts/changelog.mjs
node website/scripts/seo.mjs
node website/scripts/check.mjs
```

`website/public/changelog.html` содержит сгенерированные записи между маркерами
`changelog:start` и `changelog:end`: редактируйте их через JSON, а оформление —
в HTML/CSS. Проверка сайта отклоняет устаревшую сгенерированную страницу.
Проверьте в браузере ссылки на релизы и вид страницы на узком экране.

Обновление истории не даёт разрешения публиковать сайт. Push, включение GitHub
Pages и развёртывание сайта выполняйте только после явного одобрения владельца.

# Сайт, метаданные и аналитика

Стиль сайта: мицелий повторяет крупные ступенчатые корни главного гриба.
Статические рамки и ветви — приглушённые розовые. Teal — цвет сигнала и
отклика элементов управления: кнопки в покое тёмные, при наведении, фокусе
клавиатуры и нажатии окрашиваются в teal. Автоматические импульсы оставляйте
редкими и только у ключевой информации (условие собственного VPS и
рекомендованный релиз). Учитывайте общую настройку анимации и reduced motion.
После появления блока не оставляйте clip-path, срезающий выступающие корни.

После изменения публичных фактов, FAQ, адреса сайта или подтверждённой версии
обновляйте `website/content.json`, `website/faq.json`, `website/site.json` и генерируйте SEO командами выше.
Не редактируйте вручную блоки `seo:start` / `seo:end` и `faq:start` / `faq:end`.
Структурированные данные должны совпадать с видимым содержимым. Не обещайте
индексацию, цитирование нейросетями, снижение пинга или абсолютную защиту от DDoS.

При изменении аналитики запускайте `node --test --test-isolation=none website/analytics/server.test.mjs website/analytics/admin.test.mjs website/analytics/telegram.test.mjs website/analytics/content.test.mjs website/analytics/client.test.mjs`.
Админка обслуживается только бэкендом, вне `website/public`. Не публикуйте реальные
учётные данные, хеш пароля или cookie. Сохраняйте ограничения входа между перезапусками,
проверки Origin/CSRF, привязку и отзыв сессий; не ослабляйте их ради тестов.
Второй этап через Telegram обязателен для настроенной админки: не выдавайте сессию
после одного пароля и не добавляйте fallback при недоступности Telegram. Не храните
коды открыто, не логируйте коды и Bot API URL с токеном. Привязывайте личный чат только
по одноразовому секрету после подтверждения владельца. Бот работает через короткие
API-запросы, без отдельного процесса, webhook и фонового polling.
Не ослабляйте server-side Turnstile, привязку токенов, лимиты и доверие только к
локальному прокси ради прохождения теста. Не включайте сбор без действующего HTTPS
endpoint и ключей. Все реальные ключи, MMDB и базы статистики — вне Git и Pages;
в `website/public` не должно попадать ничего из приватной конфигурации VPS.

# Управление содержимым сайта

`website/content.json` — статический снимок текстов и релизов; `content-fields.json` — допустимые поля.
Живые данные хранятся на VPS, публично доступна только явно опубликованная редакция.
Установка бэкенда и сохранение черновика не разрешают его публикацию. Не публикуйте
черновик для проверки: используйте локальную одноразовую базу. Сохраняйте ревизии,
проверки конфликтов, историю, защиту CSRF и обязательный второй этап входа.
Релизы импортируются только из фиксированного репозитория через GitHub API; не разрешайте
произвольные URL, HTML, сценарии или загрузку файлов из редактора.
Изменения текста политики сопровождайте новой датой/редакцией. Не обещайте полного
освобождения от ответственности, не меняйте MIT скрытыми условиями сайта. Указывайте,
что перед публичным запуском рекомендуется проверка редакции профильным юристом.

Согласие на аналитику: сохраняйте отказ по умолчанию, равнозначные кнопки, отзыв с каждой страницы и остановку незавершённых запросов. Не загружайте Turnstile до согласия. При существенном изменении политики обновляйте версию NOTICE и запускайте client.test.mjs. Политика cookies не заменяет проверку правовых оснований, операторских реквизитов и поставщиков.

Владелец просит сохранять личные сведения участников команды непубличными. Не добавляйте их в сайт, документацию или примеры. Не подменяйте отсутствующие реквизиты вымышленными и не обещайте анонимность либо полное соответствие требованиям защиты данных. Необязательная аналитика сейчас выключена; сохраняйте это состояние при редактировании политики.

# Актуальность сайта и публичных материалов

При каждом публичном обновлении Mukhomor обязательно поддерживайте в актуальном состоянии сайт и особенно страницу `website/public/releases.html`: версии, платформы, статусы, файлы, ссылки и даты должны совпадать с опубликованными GitHub Releases. Обновляйте `content.json`, краткую историю, FAQ, инструкции установки, SEO и обе версии README. Сохраняйте старые выпуски.

Дизайн сайта — основной визуальный ориентир для баннеров, превью ссылок и всей статики GitHub. Снимки интерфейса получайте из актуального Slint-превью на демонстрационных данных.

Перед каждым push и загрузкой release assets проверяйте явный список файлов, исходники и содержимое архивов. Рабочие VPN-профили, секреты, данные VPS, базы, логи, локальные инструменты и материалы других проектов публиковать запрещено. Пользуйтесь allowlist и `tests/Test-PublicSource.ps1`; не добавляйте игнорируемые файлы целиком. Установка или настройка подписи сама по себе не разрешает публиковать ключи.

Для APK и Linux tar.gz запускайте `python tests/Test-PortableReleasePrivacy.py --archive ПУТЬ`: проверяются сами нативные библиотеки, включая пути в panic-строках Rust и метаданных Go. Подпись и успешная компиляция не заменяют этот контроль. Кеш исходников Go для выпуска держите внутри checkout, чтобы relative replace не раскрывал пользовательские каталоги.
